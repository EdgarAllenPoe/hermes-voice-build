# 09 — Security, retention and operational limits

## Threat model

This is a private single-user prototype on a trusted personal phone, recorder and Linux host. It is not a public upload service, a shared voice assistant, an emergency device, an authenticated voice-identification system or a sandbox around Hermes.

A person physically holding the button can record speech for your agent. BLE encryption proves the radio link's pairing relationship, **not whose voice was recorded**. A lost recorder should prompt bond review and appropriate downstream access review. Your agent's ability to send messages, delete files or make purchases remains a separate authorization concern.

## Layers provided

Physical pairing window; per-device locally generated BLE passkey; authenticated LE Secure Connections; private GATT characteristics; Tailscale reachability controls; optional HTTPS identity check; independent bearer token; input length/format/checksum validation; durable queues; restricted local file permissions; and review-first commissioning.

These controls reduce specific risks. They do not make secrets inaccessible to an administrator of the phone or Linux host, protect a physically extracted unencrypted recorder flash chip, or prevent every software vulnerability.

The raw recorder audio partition is not encrypted at rest. The Android app uses private credential-protected storage and a Keystore-protected bearer token; it does not implement additional per-recording encryption. Linux audio, transcripts and logs are ordinary private files/database pages. Use your devices' disk encryption and sensible physical custody.

## Agent safeguards

The bridge passes a prompt file using a fixed argument list; it never concatenates transcribed speech into a shell command. This prevents a class of shell injection at the bridge boundary. Hermes itself may execute tools based on the supplied message; its existing safety and approval mechanisms still matter.

Start with `delivery_mode: review`. Confirm the intended note destination and choose harmless commissioning phrases. Do not grant this prototype more account privileges than necessary. A message may be transcribed incorrectly or ambient speech may be captured accidentally.

Exactly-once external action execution is not claimed. Inspect `uncertain` jobs and Hermes's actual history before allowing any retry. Processing responses and clarification requests are logged on the host, not presented in a phone chat UI in this version.

## Secret handling

BLE pairing code: generated by `tools/provision.py`; stored in local generated firmware header and private printed card. API bearer token: generated by the server installer; stored in `~/.config/hermes-voice/token` and encrypted Android preferences. They serve different purposes and must not be reused as each other.

Keep private generated files, signing keys, tailscale login credentials and Hermes provider tokens out of public repositories and source printouts. The `.gitignore` is a convenience, not a guarantee against accidental sharing. Verify the actual archive before distributing a locally configured copy.

## Retention and backups

The recorder reclaims audio only after the phone's durable ACK. The phone clears the audio BLOB after a matching server 202 and retains a small receipt. The server retains audio, transcript, prompt and execution output so failures can be diagnosed. There is no silent automatic retention deletion in version 1.

Before moving the server database, stop both services and back up the state directory as a unit, or use SQLite's supported backup facility. Copying only the main database while a WAL is active can omit recent committed changes.

`purge-audio` clears eligible completed-message BLOBs from the server database but is not complete cleanup or secure erasure. The worker's WAV, transcript, prompt and log files remain; SQLite free pages and backups may retain old bytes. Clean these deliberately after verifying completion and backups. Do not delete receipt rows casually because they are the duplicate-delivery record.

The 100 MiB queue limit applies to BLOB contents, not the whole directory or Hermes history. Monitor free disk space and file retention. Database encryption and automatic secure-retention enforcement would be separate future work.

## Known limitations accepted for this prototype

No proven battery runtime; no measured cell temperature; no compiled target binaries in this bundle; no tested Android wake latency; 15 recorder slots; maximum 60-second messages; simple energy-based silence detection; single phone bond; no device screen or vibration; no phone display of Hermes replies; no dynamic memory of a particular interactive Hermes session; and no guarantee of complete recovery of a recording interrupted before commit.

All of these are visible design/validation boundaries, not features silently assumed to exist.

## Version 0.3 preservation and diagnostics

Permanent HTTP rejections hold the affected phone recording rather than blocking all later uploads. Corrupt recorder slots and rejected phone bytes remain private and consume storage. SKIP never deletes recorder data. Diagnostics export excludes secrets, addresses and voice content. Explicit completed-work cleanup retains duplicate receipts; it is not secure erasure. Guide 10 describes preview and apply steps.

CI Android builds use a separate package and disposable signing key. Personal builds require the retained private signing key and matching recorder provisioning. Never publish those local files.
